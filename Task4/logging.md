## Мотивация

Логирование позволит отслеживать изменения происходящие в системе в любой момент времени. Логи в связки с мониторингом позволят быстрее понять в чем причина проблемы, так как лог это журнал действий произошедших в системе.
Для компании логирование влияет на следующие показатели:

- сокращает время на разбор инцидента - повышение удовлетворенности клиента
- локализация сервиса в котором произошла проблема и какие данные повлияли на это
- более точные требования к задачам которые нужно решить для устранения проблемы, так как в логах есть пошагова инструкция что происходило

В случае нехватки ресурсов в первую очередь нужно покрыть логированием и трайсингов такие системы как:

- MES API - ключевой компонент всей системы, отсутствие логирования и трейсинга в котором не позволяет определить какие проблемы возникли с тем или иным заказом
- Shop API - компонент обслуживающий запросы пользователей, без обсервабилити сложно разбираться с возникающими проблемами пользователей что прямо влияет на зарабатываемые деньги компании

## Предлагаемое решение

Сбор логов будет организован с помощью ELK системы, для этого нужно будет развернуть следующие компоненты:

- Filebeat - агрегирует данные из разных источников
- Logstash - конвейер обработки данных
- Elastic (OpenSearch) - бд для хранения и отображения логов
- Kibana - интерфейс дл отображения и построения отчетов по логам
  Также нужно доработать компоненты системы чтобы они писали логи в правильном формате (структурированный логи).

### Политика безопасности

Чувствительные данные, такие как:

- номер телефона клиента
- пароль/код из смс
- платежные данные(номера карт и тп)
  Логироваться не будут в открытом виде, они будут заменяться в логах на шаблон (XXXXX). Для сквозной индентификации пользователя или заказа в системе будет использоваться идентификатор пользователя/заказа.

Подмена чувствительных данных на шаблон возлагается на сервисы которые эти данные пишут, для этого будут использоваться библиотеки записи логов и настроенные в этих библиотеки правила подмены тех или иных данных. При разработки задача будет проходить этап ревью и будут прогоняться линтеры по коду в автоматизированом режиме.

Доступ к логам компонента будет предоставляться только разработчикам данного компонента. Например: разработчик MES API может просматривать только логи MES API. Исключения составляют только дежурные которым на время дежурства предоставляются доступы ко всем логам системы, для проведения расследования по инцидентам. Также разработчик может запросить логи другой системы в рамках разбора инцидента, на ограниченный срок.

Логи будут хранится в отдельных индексах на компонент

| компонент | время жизни индекса | размер  | комментарий                                                                                                                                              |
| --------- | ------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| shop api  | 3 месяца            | ~50 GB  | Высокая частота запросов от пользователей (создание заказов, загрузка моделей, смена статусов). Средний размер события ~1-2KB, ~500-1000 событий/мин     |
| crm api   | 3 месяца            | ~20 GB  | Средняя частота событий (отправка в очередь, смена статусов). Средний размер события ~1KB, ~200-400 событий/мин                                          |
| mes api   | 3 месяца            | ~100 GB | Самый объемный лог из-за детального логирования прогресса расчетов (каждый этап, время выполнения). Средний размер события ~2-3KB, ~800-1500 событий/мин |

### Аллертинг и поиск аномалий

Благодаря сбору логув мы сможем организовать аллертинг, такого рода:

- число 50х или 40х в секунду/минуту/час больше определенного числа
- количество успешных запросов меньше определенного числа
- время затраченное на этап расчета стоимости больше определенного числа

И также мы сможем организовать поиск аномалий в логах такого рода:

- время нахождения заказа в определенном статусе аномально больше чем ранее
- статус заказа менялся не в той последовательности

## Обоснование выбора OpenSearch

Для системы логирования выбрана технология **OpenSearch** по следующим причинам:

### Технические преимущества

- **Open Source лицензия** - отсутствие лицензионных ограничений и возможность свободного использования без коммерческих рисков
- **Полнотекстовый поиск** - мощный механизм поиска на базе Apache Lucene позволяет быстро находить нужные логи по любым критериям
- **Высокая производительность** - эффективная индексация и поиск по большим объемам данных (суммарно ~170 GB за 3 месяца)
- **Хорошая масштабируемость** - возможность горизонтального масштабирования при росте объемов логов
- **Встроенная визуализация** - OpenSearch Dashboards предоставляет готовый инструмент для анализа и построения дашбордов

### Экономические факторы

- **Средняя стоимость владения** - баланс между функциональностью и затратами на инфраструктуру
- **Отсутствие vendor lock-in** - при необходимости можно мигрировать на совместимые решения (Elasticsearch)
- **Активное сообщество** - растущее community обеспечивает поддержку и развитие проекта

### Соответствие требованиям проекта

- **Структурированные логи** - нативная поддержка JSON и структурированных данных
- **Гибкие retention политики** - возможность настройки времени хранения индексов (3 месяца) с автоматическим удалением
- **Встроенный алертинг** - позволяет организовать уведомления о превышении порогов (50x/40x ошибки, время выполнения)
- **Множество интеграций** - легко интегрируется с Filebeat, Logstash и другими компонентами стека
- **Разделение доступов** - возможность настройки ролевой модели для ограничения доступа к индексам разных компонентов

### Альтернативы и их недостатки

- **ELK (Elasticsearch)** - ограничения Elastic License 2.0, возможные будущие ограничения функциональности
- **Splunk** - высокая стоимость коммерческой лицензии не оправдана для текущих объемов
- **Graylog** - ограниченная масштабируемость и меньшее community
- **Loki** - ограниченные возможности полнотекстового поиска (только по меткам), не подходит для детального анализа логов MES API
