# Архитектурное решение по трейсингу

## Мотивация

Трейсинг позволит нам отследить путь заказа от момента его создания до момента получения результата расчета стоимости. Это поможет нам выявить узкие места в процессе обработки заказа, а также понять, на каком этапе возникает проблема, если заказ не обрабатывается должным образом.

### Бизнес-метрики на которые может повлиять трейсинг:

- время от создания заказа до получения результата расчета стоимости
- количество заказов, которые не были обработаны должным образом из-за ошибок или таймаутов
- уменьшение времени отладки проблем
- уровень удовлетворенности клиентов, который может быть повышен за счет более быстрого решения проблем с заказами
- улучшение качества продукта, так как даже одну ошибку можно отследить и исправить
- обнаружение узких мест в процессе обработки заказов, что позволит оптимизировать процесс и улучшить качество обслуживания клиентов

## Проблемные места

- пользователь отправил заказ - возникла ошибка или таймаут в shop api
- shop api пошел в бд, но запрос стал выполняться слишком долго
- shop api пошел в s3 и запрос на загрузку выполнялся долго, клиент не дождался
- crm api выбор заказа из shop db, возможно долгое время ответа
- crm api отправка заказа в очередь на обработку - таймаут при отправки или ошибка
- mes api получение сообщения из очереди- возможно таймаут
- mes api расчет стоимости и изменение статуса заказа в своей бд - возможен тацмаут и прерванное задание рассчета(например при рестарте)
- mes api таймаут при получении модели из s3
- mes api получает заказ на расчет по апи, таймаут от бд
- mes -> mes api отображение заказов в интерфейсе мес, возможен таймаут или долгое выполнение запросов в бд

## Данные которые должны попадать в трейсинг:

- индентификатор пользователя
- индетификатор заказа
- статус заказа
- название файла из s3 во время четения и расчета стоимости

## Предлагаемое решение

Трейсинг будет реализован с помощью open source продукта Open Telemetry (OTel), для этого будут установлены следующие компоненты:

- коллектор для телеметрии с reciver`ом (например, OpenTelemetry Collector)
- UI для отображения данных о трейсинге (например, Jaeger )
- также будет использоваться SDK для интеграции с приложением (например, OpenTelemetry SDK для Python)

### Автоматический мониторинг прохождения заказа

1. пользователь регистрируется/авторизуется в системе, при этом в трейсинг будет добавляться информация об account_id
2. при создании заказа в shop api будет генерироваться уникальный идентификатор заказа (order_id), который будет использоваться для трейсинга, вместе с account_id
3. пользователей подгружает 3d модель из s3, при этом в трейсинг будет добавляться информация о названии файла и времени загрузки, вместе с account_id и order_id
4. после загрузки модели, shop api отправляет заказ в очередь на обработку, при этом в трейсинг будет добавляться информация о статусе заказа и времени отправки, вместе с account_id и order_id + специальный заголовок OTel для отслеживания связи между сервисами
5. как только mes api получит сообщение из очереди, он будет обрабатывать заказ и добавлять информацию о статусе заказа и времени обработки в трейсинг, вместе с account_id и order_id + специальный заголовок OTel для отслеживания связи между сервисами
6. после подсчета стоимости заказа, оператор через mes интерфейс будет менять ему статусы и при этом отправлять информацию о статусе заказа и времени изменения статуса в трейсинг, вместе с order_id + специальный заголовок OTel для отслеживания связи между сервисами
7. после доставки заказа оператор меняет статус закакза на "закрыт", при этом отправляет информацию о статусе заказа и времени изменения статуса в трейсинг, вместе c order_id + специальный заголовок OTel для отслеживания связи между сервисами

На каждом этапе трейсы попадают в кибану и там настроен allerting, который будет уведомлять ответственных сотрудников о проблемах с заказами, например если заказ не был обработан в течение определенного времени или если возникла ошибка при обработке заказа. Это позволит нам быстро реагировать на проблемы и обеспечивать высокий уровень обслуживания клиентов.

Итого, трейсинг будет содержать информацию о каждом этапе обработки заказа, что позволит нам отследить путь заказа и выявить узкие места в процессе обработки заказов, а kibana будет использоваться для мониторинга и алертинга, что позволит нам быстро реагировать на проблемы и обеспечивать высокий уровень обслуживания клиентов.

## Компромисы

Проблемы которые мешают интеграции или для которых телеметрия не походит:

- ключевая система(MES API) разработана внешним разработчиком, то интеграция OTel SDK может оказаться слишком дорогой с точки зрения времени и ресурсов.
- трейсинг без логирования не поможет разобраться почему тот или иной код работает медленно и в каком именно месте происходят проблемы
- также трейсинг это не метрики а именно отладка какой-то конкретной проблемы, поэтому он не поможет отследить общую производительность системы и выявить узкие места в целом, для этого нужны метрики

## Безопасность

Система трейсинга будет обрабатывать чувствительные данные, такие как идентификаторы пользователей и заказов. Поэтому необходимо обеспечить безопасность данных, чтобы предотвратить несанкционированный доступ и утечку информации. Для этого будут применены следующие меры:

- будет настроена аутентификация и авторизация для доступа к данным трейсинга, чтобы только уполномоченные лица могли просматривать и анализировать данные
- в тресинге не будет храниться информация которая может идентифицировать конкретного пользователя, например имя или email, вместо этого будут использоваться анонимные идентификаторы
- в случае обнаружения подозрительной активности или утечки данных, чтобы предотвратить дальнейшее распространение информации - трейсинг будет выключен
- будет ввести аудит доступа к данным трейсинга, чтобы отслеживать кто и когда обращался к данным, а также какие действия выполнялись с этими данными
