# Архитектурное решение по кешированию

## Мотивация

Кеширование является важной частью архитектуры программного обеспечения, особенно в системах с высокой нагрузкой и большим количеством запросов. Оно позволяет уменьшить время отклика системы, снизить нагрузку на базу данных и улучшить общую производительность приложения. Предлагается внедрить кеширование в сервтсы:

- MES API - кешировать заказы и их статусы, чтобы уменьшить количество обращений к базе данных при повторных запросах от операторов.
- Internet Shop/Shop API - кишировать информацию о заказах и их статусах, чтобы ускорить обработку запросов от клиентов.

## Предлагаемое решение

### Internet Shop/Shop API

В Internet Shop/Shop API предлагается использовать кеширование на уровне клиента с TTL равным 5-10 минутам, что позволит уменьшить количество запросов к Shop API. При этом, если данные устарели, клиент будет получать актуальную информацию при следующем запросе и на стороне Shop API также будет находиться кеширование (серверное).

Патерн кеширования, который предлагается использовать, это кеширование с использованием ключей, основанных на идентификаторах заказов. При этом из-за того что в бд Shop API CRM имеет доступ напрямую, то в качестве патерна обновления кеша будем использовать Read-Through кеш будет находиться на стороне БД. Плюсы такого подхода заключаются в том, что при изменении данных в базе данных, кеш автоматически обновляется, что позволяет избежать проблем с устаревшими данными, что свойственно другим патернам кеширования, так как они находяться на стороне приложений.

В качестве стратегии инвалидации кеша предлагается использовать TTL (Time To Live) для каждого объекта в кеше. Это позволит автоматически удалять устаревшие данные из кеша через определенное время, что обеспечит актуальность информации. Ну и при изменении заказа данные этого заказа обновляются.

### Mes Api

Для кеширования в сервисе MES API будет использоваться серверное кеширование, так как пользователи получают один и тот же список заказов и нет разницы какой оператор их запросил. В качестве ключа кеширования будет использоваться идентификатор заказа.
В качестве патерна кеширования будет применяться write-behind, инвалидация будет происходить в момент обновления/создания заказа + у каждого объкта в кеше будет выставлен TTL. Данный патерн проявит себя хорошо, так как при изменении заказа он обновит определенный заказ и оператор запросивший список получит их из кеша с обновленным уже заказом

В качестве стратегии инвалидации была выбрана стратегия основаная на времени жизни объекта в кеше (TTL). Это позволит автоматически удалять устаревшие данные из кеша через определенное время, что обеспечит актуальность информации. Также при изменении заказа данные этого заказа будут обновляться в кеше.
