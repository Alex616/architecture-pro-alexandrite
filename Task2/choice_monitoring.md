# Выбор и настройка мониторинга в системе

## Мотивация

Мониторинг позволяет определить почему у пользователя возникла та или иная проблема и что нужно сделать для ее решения. Также благодаря мониторингу можно находить узкие места системы до того момента как туда попадут реальные пользователи.

Для компании это означает что будет меньше проблем у пользователей, а те что будут будут решаться быстрее как следствие больше довольных клиентов. Также благодаря выявлению узких мест, например критический уровень La на серверах мес, можно более точечно обновлять железо и концентрироваться на проблемах которые могут наступить в ближайшее время. Ну и благодаря понимаю насколько нагружена система можно прогнозировать необходимые действия при внедрении нового функционала, что увеличит шансы на успех этого функционала.

## Выбор подхода к мониторингу

Для MES API системы - USE подход
Для MES, CRM, Internet Shop - RED подход
Для shop api, crm api, частично для mes api - четыре золотых сигнала
Для баз данных и очереди -USE подход

### Общие метрики

- order_proccess_time_per_status - время затраченое на обработку заказа, ярлыки(ид заказа, статус заказа) - поможет выявить узкие места в обработки заказов, и также общее количество обрабатываемых заказов

### MES API метрики

- order_execution_time - время за которое рассчитывается стоимость модели
- number_of_message_in_rabbit - число сообщений в очереди, позволяет следить за производительностью системы
- dead_letter_exchange - число обработанных с ошибкой сообщений, ярлык - код ошибки
- api_rps -количество запросов в секунду
- latency -время ответа
- errors - ошибка запроса, ярлык - статус код ответа, по статус коду можно отделить 500 от 400
- percent_cpu - процент загружености цпу, поможет определить что мы скоро упремся в цпу и вовремя проапгрейдить сервер
- mem_utilisation - количество свободной памяти, также поможет вовремя выявить проблемы с устариванием и проблемы связаные с кешом или утечкой памяти
- number_open_connections_on_db - количество открытых соединений до бд, обычно рост этого показателя и отсутствие роста рпс - говорит о проблемах с закрытыми конектами, что в дальнейшем выливается в отказ обслживания когда количество доступных коннектов бд истечет
- mem_utilization_db утилизация памяти бд, при сложных запросах не попадающих в индекс может возникнуть рост потребления памяти
- db_size - размер бд, при увеличении данных бд может расти за этим нужно следить чтобы вовремя увеличить место на диске

### MES CRM

- page_open_time - время открытия страницы, ярлык - код/название страницы, показывает как пользователь видит и использует сайт
- mes_api_response_time - время ответа апи мес, ярлык имя/код команды - если апи будет медленно отвечать то и страницы будут медленно загружаться, позволяет увидеть где именно мы медленно отвечаем

### CRM API

- api_rps -количество запросов в секунду
- latency -время ответа
- errors - количество ошибок, все тоже что и у mes crm
- percent_cpu - процент загружености цпу, все тоже что и у mes crm
- mem_utilisation - количество свободной памяти, все тоже что и у mes crm
- rabbit_errors - количество ошибок при отправки сообщений, ярлык- некий код, по которому можно будет отфильтровать ошибки, позволит вовремя выявить проблемы с отправкой заказов на обработку
- s3_latency -время чтения из s3, позволяет понять есть ли проблемы при чтении из s3
- shop_db_latency -время чтения из бд магазина, ярлык имя таблицы/вьюхи/хеш-запроса, позволяет обнаружить на каких запросах мы тормозим

### Internet shop

- page_open_time - среднее время открытие страницы, все тоже что и у mes crm
- shop_api_response_time - время ответа апи магазина, ярлык имя/код команды - если апи будет медленно отвечать то и страницы будут медленно загружаться, позволяет увидеть где именно мы медленно отвечаем

### Shop Api

- api_rps -количество запросов в секунду
- latency -время ответа
- errors - количество ошибок, все тоже что и у mes api
- percent_cpu - процент загружености цпу, все тоже что и у mes api
- mem_utilisation - количество свободной памяти, все тоже что и у mes api
- number_open_connections_on_db - количество открытых соединений до бд, все тоже что и у mes api
- mem_utilization_db утилизация памяти бд, все тоже что и у mes api
- db_size - размер бд, все тоже что и у mes api
- s3_capacity - потребленный объем s3 хранилища, ярлык - имя бакета, позволяет выявить момент когда нужно будет расширять объем хранилища

## Показатели насыщености

1. Рост количества сообщений в очереди - в этом случае нужно добавлять инстансов с мес приложением, для ускорения обработки сообщений.
2. Отслеживания времени нахождения заказа в определенном статусе, если время выходит за определенный предел, то в зависимости от статуса нужно чинить определенный сервис. Например если заказ висит долго в статусе SUBMITTED то проблема либо с тем что много заказов и мес не справляется(нужно добавить инстансов), либо мес долго считает и тогда нужно подумать об улучшении сервера.Или если заказ завис в MANUFACTURED_APPROVED, то есть проблемы с производством.
3. Также следить за утилизацией серверов (La) и планировать ежегодный апгрейд серверов
4. Следить за метриками открытия страниц у пользователей и в случае медленного (больше 500 мс), начинать оптимизацию страницы:
   - ускорять ответы апи бекенда
   - использовать меньше команд для прорисовки страницы
   - добавлять в команды апи необходимые данные, чтобы уменьшить число запросов
